==================================================
PHASE 1 — CAPTURE EXACT FAILURES
==================================================

Untuk masing-masing dari 3 failure, catat:

- test name;
- expected;
- actual;
- stack trace;
- mocked function state;
- route response;
- DB mock calls;
- cache state;
- fingerprint state.

Jangan menebak root cause dari summary pendek.

==================================================
PHASE 2 — TRACE FAILURE HANDLING
==================================================

Baca seluruh failure path pada submit/create route.

Verifikasi urutan berikut:

claimFingerprint
→ project transaction
→ related inserts
→ commitFingerprint
→ response

Pada error:

- releaseFingerprint harus dipanggil;
- in-memory cache tidak boleh menyimpan success;
- partial project tidak boleh tersisa;
- duplicate retry harus dapat mencoba ulang;
- error response harus konsisten.

Periksa kemungkinan:

- releaseFingerprint tidak terpanggil pada semua catch path;
- commitFingerprint dipanggil terlalu awal;
- cache diisi sebelum seluruh insert selesai;
- test mock tidak sesuai shape return sebenarnya;
- transaction mock tidak menjalankan callback seperti production;
- duplicate path mengembalikan status berbeda dari assertion;
- response payload berbeda antara first request dan dedup retry.

==================================================
PHASE 3 — FIX TESTS OR CODE BASED ON REAL CAUSE
==================================================

Aturan keputusan:

Jika production code salah:
- perbaiki production code;
- tambahkan regression assertion.

Jika test mock salah:
- perbaiki mock agar mencerminkan real DB/service contract;
- jangan mengubah production code hanya untuk test.

Jika assertion salah:
- ubah assertion ke canonical behavior;
- jangan sekadar menurunkan strictness.

Jika async race menyebabkan flaky test:
- gunakan barrier/deferred promise;
- jangan memakai arbitrary sleep sebagai satu-satunya sinkronisasi.
