PHASE V4.0B — RUNTIME ROSTER & CUSTOMER PROJECT LINKAGE

Audit V4.0A telah selesai dan tersimpan di:

docs/phase-v4.0a-runtime-audit.md

Baca dokumen audit tersebut secara menyeluruh sebelum mengubah kode.

Temuan utama dari V4.0A:

1. Runtime nyata customer saat ini berjalan melalui:
   creativeWorkflowRunner
   → creative_project_steps
   → genuine provider/LLM executions

2. Sistem ai_jobs / ai_workers / dispatcher berjalan paralel tetapi belum menerima job customer yang nyata.

3. Sistem ai_agents berfungsi sebagai digital workforce/org chart dan terpisah dari runtime execution.

4. Customer Workspace AI Workforce masih menggunakan roster, status, dan confidence frontend yang sebagian hardcoded/demo.

5. Belum ada realtime channel.

6. Cost tracking masih estimated, belum actual.

==================================================
TUJUAN V4.0B
==================================================

Hubungkan customer project dan workspace ke roster AI worker yang nyata, tanpa:

- memindahkan runtime existing;
- mengganti creativeWorkflowRunner;
- membuat dispatcher baru;
- mengaktifkan ai_jobs sebagai source of truth;
- membuat SSE/WebSocket;
- mengubah workflow execution;
- mengubah provider invocation;
- mengubah business flow;
- membuat progress palsu.

Fase ini hanya membangun fondasi relasi dan API snapshot worker/project yang jujur.

==================================================
PRINSIP ARSITEKTUR
==================================================

Untuk V4.0B:

- creativeWorkflowRunner tetap menjadi execution engine aktif.
- creative_project_steps tetap menjadi source of truth execution step.
- ai_agents dapat menjadi source metadata roster/role jika datanya valid.
- ai_jobs / ai_workers belum dijadikan source of truth.
- jangan menyatukan ketiga sistem secara paksa pada fase ini.
- jangan membuat migrasi besar.
- gunakan adapter/read-model jika memungkinkan.
- data demo frontend hanya diganti bila source runtime nyata tersedia.

LANGKAH 2 — TENTUKAN SOURCE OF TRUTH V4.0B
==================================================

Gunakan model berikut:

Execution source:
creative_project_steps

Worker role metadata source:
ai_agents jika tersedia dan valid

Customer project source:
existing project/request table

Workspace source:
existing workspace API

Buat mapping yang jelas:

customer_project
→ creative workflow/project
→ creative_project_steps
→ agent/worker role metadata
→ workspace runtime roster

Jangan membuat relasi fiktif.

==================================================
LANGKAH 3 — AUDIT RELASI PROJECT
==================================================

Pastikan dapat menjawab:

- customer workspace project ID menunjuk ke tabel apa?
- creativeWorkflowRunner menerima project/request ID apa?
- creative_project_steps memiliki foreign key apa?
- apakah project customer dapat ditelusuri langsung ke creative_project_steps?
- apakah step memiliki agent role?
- apakah step memiliki model/provider?
- apakah step memiliki startedAt/completedAt?
- apakah step memiliki status dan error?
- apakah output/artifact reference tersedia?

Jika linkage sudah ada, gunakan.

Jika linkage belum lengkap, usulkan perubahan paling minimal.

==================================================
LANGKAH 4 — MINIMAL DATA MODEL
==================================================

Prioritaskan tanpa migration.

Pertama coba membuat adapter/read-model dari data existing.

Migration hanya diperbolehkan jika benar-benar diperlukan.

Jika diperlukan, perubahan minimal boleh mencakup salah satu:

- customerProjectId pada creative workflow record;
- agentRoleKey pada creative_project_steps;
- agentId nullable pada creative_project_steps;
- metadata JSON untuk provider/model/display role;
- index untuk project/step lookup.

Jangan menambahkan tabel baru kecuali audit membuktikan tidak ada alternatif aman.

Sebelum migration:

- jelaskan alasan;
- cek data existing;
- buat rollback plan;
- pertahankan backward compatibility.

==================================================
LANGKAH 5 — CANONICAL WORKER SNAPSHOT
==================================================

Buat internal normalized type, misalnya:

RuntimeWorkerSnapshot

Field yang diperbolehkan:

- id
- roleKey
- displayName
- department
- specialty
- stepId
- stepName
- status
- currentTask
- provider
- model
- startedAt
- completedAt
- outputCount
- attempt
- isHuman
- source
- isLive

Status harus diturunkan dari creative_project_steps.

Contoh mapping:

pending → queued
in_progress/running → working
completed → completed
failed → failed
waiting_review → reviewing
blocked → blocked

Gunakan status existing yang nyata.

Jangan membuat status random.

==================================================
LANGKAH 6 — CONFIDENCE DAN ETA
==================================================

Untuk fase ini:

- hapus confidence demo pada worker live;
- jangan membuat angka confidence baru;
- jika confidence tidak tersedia, jangan tampilkan field;
- ETA hanya ditampilkan jika ada delivery/step estimate nyata;
- jika tidak tersedia, tampilkan “Estimating…” atau sembunyikan.

Jangan memakai seed, hash ID, atau angka statis untuk confidence.

==================================================
LANGKAH 7 — WORKER ROSTER ADAPTER
==================================================

Buat service/adapter backend yang membangun roster dari:

1. creative_project_steps;
2. ai_agents metadata jika dapat dicocokkan;
3. workflow step configuration;
4. provider/model execution metadata.

Urutan prioritas:

runtime step data
→ ai_agents metadata
→ safe role fallback

Fallback harus jujur.

Contoh:

Role: “Creative AI Worker”
Source: workflow-step
isLive: true

Jangan membuat nama manusia atau avatar palsu.

==================================================
LANGKAH 8 — WORKSPACE API EXTENSION
==================================================

Audit workspace project detail endpoint existing.

Jangan membuat endpoint baru jika response existing dapat diperluas dengan aman.

Tambahkan runtime field, misalnya:

runtime: {
  source: "creative_workflow",
  isLive: true,
  workers: RuntimeWorkerSnapshot[],
  currentWorkerId: string | null,
  currentStepId: string | null,
  lastUpdatedAt: string | null
}

Pastikan:

- backward compatible;
- field baru optional;
- existing frontend tidak rusak;
- ownership/token validation tetap sama;
- tidak expose internal prompt/error/secret;
- tidak expose cost/provider credential.

Jika endpoint existing tidak cocok, usulkan endpoint baru hanya setelah menjelaskan alasannya.

==================================================
LANGKAH 9 — CURRENT TASK
==================================================

Current task harus berasal dari step runtime aktual.

Prioritas:

1. running step;
2. waiting_review step;
3. latest completed step;
4. next pending step;
5. no active task.

Response minimal:

- step name
- public task label
- worker role
- status
- startedAt
- provider/model bila aman
- lastUpdatedAt

Jangan menggunakan stage-to-worker hardcoded mapping di frontend jika backend sudah mengirim current task.

==================================================
LANGKAH 11 — FALLBACK BEHAVIOR
==================================================

Workspace harus tetap stabil jika:

- project lama tidak memiliki creative_project_steps;
- workflow belum dimulai;
- ai_agents tidak memiliki mapping;
- provider/model kosong;
- runtime query gagal;
- no workers assigned;
- project sudah completed;
- project failed.

Gunakan state jujur:

- “AI team will appear when production starts.”
- “Runtime data is not available for this project.”
- “Production has completed.”
- “A workflow step needs attention.”

Jangan menampilkan lima worker default seolah-olah mereka live.

==================================================
LANGKAH 12 — SECURITY
==================================================

Audit dan test:

- workspace token ownership;
- project belongs to token;
- step belongs to project;
- no cross-project worker leakage;
- no cross-tenant leakage;
- no raw provider response;
- no hidden prompt;
- no internal error stack;
- no API key;
- no system prompt;
- no internal-only metadata.

Runtime roster response hanya boleh berisi customer-safe fields.
