TAHAP 3 — P0-1 TENANT ISOLATION SPECIFICATION
=============================================

Buat spesifikasi rinci untuk tenant isolation.

Harus mencakup:

A. Tenant Resolution Matrix

Buat tabel untuk setiap jenis akses:

* authenticated customer
* authenticated admin
* platform super admin
* public project token
* public quotation token
* public vendor submission token
* worker
* scheduler
* webhook
* SSE client
* export download
* signed storage URL

Untuk setiap jenis akses tentukan:

* sumber tenant
* cara validasi
* fallback
* kondisi penolakan
* actor type
* audit event

B. Entity Classification

Kelompokkan tabel menjadi:

* tenant-owned
* globally shared
* platform administration
* reference/master data
* transitional/legacy
* ambiguous and requiring decision

Untuk setiap tabel tenant-owned tentukan tenant key canonical-nya.

C. Query Enforcement

Petakan semua query penting yang saat ini belum tenant-safe.

Untuk setiap query:

* file
* function
* tabel
* operasi read/write/delete
* cara tenant filter akan diterapkan
* apakah membutuhkan repository baru
* apakah membutuhkan perubahan signature service

D. Public Token Resource-Derived Tenant

Tentukan alur:

token
→ resolve resource
→ derive tenant
→ validate token scope
→ create tenant context
→ execute service

Dilarang mempercayai `tenantId` dari body, query parameter, atau header publik.

E. Worker and Scheduler

Tentukan perubahan payload job agar selalu membawa:

* tenantId
* actorType system
* originatingRequestId
* originatingActorId jika tersedia
* resourceId
* projectId/orderId jika relevan

Tentukan perlakuan terhadap job lama yang belum memiliki tenantId.

F. SSE

Tentukan:

* tenant-scoped channel
* resource authorization
* reconnect cursor validation
* prevention of cross-tenant event replay
* summary/event filtering
* admin visibility rules

G. RLS

Tentukan:

* tabel yang layak memakai RLS
* tabel yang belum aman diaktifkan langsung
* kebijakan staged rollout
* service-role exception
* cara memastikan backend tidak bergantung hanya pada service-role bypass

H. Acceptance Criteria

Minimal:

* tidak ada tenant-owned query tanpa tenant scope
* public token tidak dapat berpindah tenant
* worker tidak memproses resource tenant lain
* SSE tidak dapat membaca event lintas tenant
* export tidak dapat diunduh tenant lain
* test cross-tenant read/write/delete seluruhnya gagal secara aman

TAHAP 6 — P0-2 SOFT DELETE SPECIFICATION
========================================

Klasifikasikan setiap entitas menjadi:

1. Soft-delete mandatory
2. Archive-only
3. Immutable
4. Hard-delete permitted
5. Retention-controlled purge
6. Reference/master data

Definisikan kolom standar:

* deleted_at
* deleted_by
* deletion_reason
* restored_at
* restored_by
* archived_at jika archive berbeda dari delete
* purge_after jika diperlukan

Tentukan perbedaan jelas antara:

* archive
* soft delete
* restore
* purge

Untuk setiap entitas mandatory:

* file schema
* service yang berubah
* route yang berubah
* query yang harus exclude deleted secara default
* relasi anak
* restore behavior
* unique constraint behavior
* audit event
* retention rule

Audit seluruh hard delete aktual, termasuk yang ditemukan di `cp-review.ts`.

Tentukan:

* mana yang harus diganti soft delete
* mana yang dapat tetap hard delete
* mana yang harus dibatasi platform admin
* mana yang membutuhkan approval ganda

Tentukan kebijakan cascading:

* jangan otomatis soft-delete seluruh child tanpa keputusan eksplisit
* child immutable seperti audit event tidak boleh ikut dihapus
* deliverable/file harus mempertimbangkan storage retention
* quotation accepted tidak boleh dipurge tanpa retention policy

TAHAP 7 — P0-4 CANONICAL QUOTATION SPECIFICATION
================================================

Tetapkan:

* `ai_quotations` sebagai canonical
* `creative_project_quotations` sebagai legacy yang dipensiunkan bertahap

Buat spesifikasi fase:

Phase Q1 — Inventory and Compatibility

* petakan seluruh route, service, UI, worker, notification, dan laporan yang menggunakan kedua tabel
* petakan perbedaan field dan behavior
* identifikasi data yang tidak dapat dipetakan langsung

Phase Q2 — Freeze Legacy Create

* hentikan create baru ke legacy
* pertahankan read kompatibel
* tampilkan telemetry saat legacy path masih dipanggil
* buat audit event untuk legacy-path usage

Phase Q3 — Dual Read / Canonical Write

* semua write menuju `ai_quotations`
* read lama menggunakan compatibility adapter
* tidak boleh ada dual write kecuali dibuktikan benar-benar diperlukan

Phase Q4 — Data Migration

* mapping field
* deduplication
* conflict resolution
* status normalization
* tenant assignment
* audit history preservation
* idempotency
* rollback markers

Phase Q5 — Consumer Cutover

* admin portal
* customer portal
* public approval token
* notifications
* analytics
* audit
* exports

Phase Q6 — Legacy Retirement

* tandai deprecated
* blok route
* observability period
* arsipkan tabel
* jangan drop tabel sebelum retention dan rollback window selesai

Tentukan canonical quotation state machine.

Minimal evaluasi status:

* draft
* prepared
* sent
* viewed
* revision_requested
* accepted
* rejected
* expired
* superseded
* archived

Tentukan transisi yang valid, aktor yang diizinkan, audit event, dan side effect.

TAHAP 14 — DEFINITION OF DONE
=============================

P0 dianggap selesai hanya jika:

* seluruh tenant-owned query memiliki enforcement
* worker dan scheduler membawa tenant context
* SSE dan export tenant-safe
* audit event canonical dan konsisten
* operasi kritis memakai audit log transactional
* hard delete berisiko sudah diganti atau dibatasi
* restore dan retention memiliki aturan jelas
* semua quotation baru memakai `ai_quotations`
* legacy quotation create telah diblok
* compatibility read teruji
* seluruh security test lintas tenant lulus
* seluruh regression test existing tetap lulus
* dokumentasi arsitektur dan runbook diperbarui
* tidak ada klaim selesai tanpa bukti test dan runtime verification
