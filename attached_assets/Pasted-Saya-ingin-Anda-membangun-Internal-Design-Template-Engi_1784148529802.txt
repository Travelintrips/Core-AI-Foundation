Saya ingin Anda membangun **Internal Design Template Engine** untuk platform AI Creative yang sudah ada.

Tujuan utama sistem ini:

1. AI hanya membuat desain/template sekali.
2. Template disimpan dalam format JSON yang reusable.
3. Untuk menghasilkan 100–10.000 desain, sistem hanya mengganti data dinamis seperti teks, gambar, logo, harga, warna, dan QR code.
4. Sistem tidak boleh memanggil image-generation AI untuk setiap hasil.
5. Rendering dilakukan oleh worker internal menggunakan template yang sama.
6. Hasil akhir dapat diekspor menjadi PNG, JPG, WebP, dan PDF.
7. Proses harus mendukung batch rendering, queue, retry, idempotency, progress tracking, dan tenant isolation.

Gunakan stack yang sudah ada dalam repository. Jangan membuat aplikasi terpisah jika tidak diperlukan.

Stack utama:

* Backend: Node.js, TypeScript, Express
* Database: PostgreSQL/Supabase
* ORM: Drizzle ORM
* Frontend: React, Vite, Tailwind, Shadcn UI
* Storage: gunakan storage abstraction yang sudah ada
* Queue: gunakan job/worker infrastructure yang sudah ada
* Renderer: pilih implementasi yang paling stabil antara SVG + Sharp atau HTML/CSS + Playwright
* Editor visual: gunakan Fabric.js atau Konva.js hanya jika repository belum memiliki canvas editor

Jangan langsung menulis kode sebelum melakukan audit terhadap:

* struktur monorepo,
* sistem job worker yang sudah ada,
* storage service,
* tenant/request context,
* authentication dan authorization,
* asset management,
* design/document/presentation engine yang sudah ada,
* pola database dan migration,
* logging dan error handling,
* frontend routing dan design system.

Jangan membuat duplikasi terhadap service, context, renderer, queue, storage, atau repository pattern yang sudah tersedia.

## B. Template Schema

## C. Template Variable System

Buat variable registry.

Jenis variable minimal:

```ts
type TemplateVariableType =
  | "text"
  | "number"
  | "currency"
  | "image"
  | "color"
  | "url"
  | "date"
  | "boolean";
```

Contoh:

```json
{
  "key": "product_name",
  "label": "Product Name",
  "type": "text",
  "required": true,
  "defaultValue": "Product Name",
  "validation": {
    "maxLength": 80
  }
}
```

Contoh binding di element:

```json
{
  "type": "text",
  "value": "{{product_name}}"
}
```

atau gunakan binding object yang lebih aman:

```json
{
  "type": "text",
  "binding": {
    "variableKey": "product_name",
    "fallback": "Product Name"
  }
}
```

Lebih utamakan binding object daripada string replacement mentah untuk mencegah injection dan kesalahan parsing.

Tambahkan formatter:

* currency,
* number,
* percentage,
* date,
* uppercase,
* lowercase,
* title case,
* truncate.

Tambahkan conditional visibility sederhana:

```json
{
  "visibleWhen": {
    "variable": "show_price",
    "operator": "equals",
    "value": true
  }
}
```

Jangan membuat expression engine yang mengeksekusi JavaScript dari user.

## E. Renderer

Pilih salah satu strategi utama setelah audit.

### Pilihan utama yang disarankan: SVG + Sharp

Gunakan SVG sebagai intermediate render format karena:

* lebih ringan daripada membuka browser untuk setiap item,
* mudah mengatur teks, gambar, shape, dan clipping,
* Sharp dapat menghasilkan PNG, JPG, dan WebP,
* cocok untuk batch rendering skala besar.

Alur:

```text
Template JSON
   ↓
Resolve Variables
   ↓
Build SVG
   ↓
Sharp Render
   ↓
PNG/JPG/WebP
```

Untuk PDF, gunakan:

* PDFKit,
* SVG-to-PDF,
* atau library yang sudah ada dalam repository.

Gunakan Playwright/Chromium hanya jika fitur HTML/CSS yang dibutuhkan tidak dapat dicapai dengan SVG.

Jangan membuka satu browser baru untuk setiap render.

Jika Playwright diperlukan:

* gunakan browser pool,
* reuse browser context secara aman,
* batasi concurrency,
* tutup page setelah render,
* tambahkan timeout,
* cegah request eksternal sembarangan.

Renderer harus deterministic.

Input template dan data yang sama harus menghasilkan output visual yang sama sejauh font dan asset tidak berubah.

## F. Font Handling

Buat font registry.

Hanya izinkan font yang sudah terdaftar dan memiliki lisensi penggunaan.

Simpan metadata:

* font family,
* font weight,
* file reference internal,
* supported styles.

Renderer tidak boleh mengambil font acak dari URL eksternal pada saat render.

Jika font tidak tersedia:

1. gunakan fallback font yang ditentukan template,
2. jika tidak ada, gunakan fallback platform,
3. catat warning dalam render metadata.

Jangan membagikan atau mengekspos file font secara publik tanpa izin lisensi.

## G. Asset Handling

Semua gambar input harus melalui asset service.

Dukung:

* upload file,
* image URL import jika diizinkan,
* internal storage asset,
* image validation,
* MIME validation,
* size limit,
* timeout,
* corrupted file detection,
* image dimension extraction.

Sebelum render:

* download atau resolve asset,
* cache asset secara lokal sementara,
* batasi domain remote jika URL eksternal diizinkan,
* cegah SSRF,
* hapus temporary file setelah selesai.

Tambahkan fallback placeholder jika gambar produk tidak tersedia.

## H. Batch Rendering

User harus dapat:

1. memilih template,
2. mengunggah CSV/XLSX atau memasukkan data dari database,
3. memetakan kolom dataset ke template variables,
4. melihat preview beberapa baris,
5. memulai batch render,
6. melihat progress,
7. retry item gagal,
8. mengunduh hasil individual atau ZIP.

Contoh data:

```json
[
  {
    "product_name": "Coconut Charcoal Briquette",
    "price": "USD 1,200 / MT",
    "product_image": "asset-id-1",
    "country": "Indonesia"
  },
  {
    "product_name": "Palm Acid Oil",
    "price": "USD 750 / MT",
    "product_image": "asset-id-2",
    "country": "Indonesia"
  }
]
```

Jangan memasukkan seluruh dataset besar ke satu job.

Gunakan:

```text
1 Batch
  ├── Render Item 1
  ├── Render Item 2
  ├── Render Item 3
  └── Render Item N
```

Batch hanya menjadi parent/aggregator.

Setiap render item harus dapat di-retry sendiri.

## I. Queue dan Worker

Integrasikan dengan worker/job system yang sudah tersedia.

Tambahkan job type seperti:

```text
design_render
design_render_batch_dispatch
design_render_zip_export
```

Worker harus:

* mengambil template version yang immutable,
* memvalidasi input data,
* resolve variables,
* resolve assets,
* render,
* upload ke storage,
* menyimpan output,
* memperbarui progress batch,
* menangani retry,
* mencatat error terstruktur.

Tambahkan configurable concurrency:

```env
DESIGN_RENDER_CONCURRENCY=4
DESIGN_RENDER_MAX_ATTEMPTS=3
DESIGN_RENDER_TIMEOUT_MS=60000
DESIGN_RENDER_MAX_BATCH_SIZE=10000
```

Nilai default harus aman untuk resource Replit.

Jangan menjalankan 1.000 render secara paralel.

Gunakan bounded concurrency.

## P. Overflow Protection

Renderer wajib menangani:

* teks terlalu panjang,
* image missing,
* image aspect ratio berbeda,
* variable kosong,
* unsupported font,
* invalid color,
* output dimension terlalu besar,
* corrupted asset,
* QR terlalu panjang,
* element keluar dari canvas.

Implementasikan overflow policy:

```text
Text:
1. wrap
2. reduce font size sampai minimum
3. truncate/ellipsis jika masih tidak muat
4. simpan warning

Image:
1. cover/contain sesuai template
2. clip dalam frame
3. gunakan fallback jika gagal
```

Preview dan final render harus menggunakan logic layout yang sama agar hasil tidak berbeda.
