A2 — RATE LIMITER LIVE WIRING
==================================================

Gunakan DESIGN_RATE_LIMIT_POLICIES dan limiter framework existing.

Pasang limiter minimal pada:

- design AI execution;
- design render;
- design export;
- design upload;
- public design review/token endpoint;
- signed URL generation endpoint jika ada.

Rate-limit key:

Authenticated routes:
tenantId + actorId + capability

Public token routes:
token fingerprint + IP

Render/export:
tenantId + projectId + operation

Requirements:

- jangan log raw token;
- jangan gunakan raw authorization header;
- structured HTTP 429;
- Retry-After bila framework mendukung;
- invalid limiter configuration fail-closed untuk expensive endpoints;
- tenant A tidak menghabiskan quota tenant B;
- public-token rate limit terpisah dari authenticated actor.

Tambahkan integration tests yang membuktikan middleware benar-benar dipanggil
oleh route nyata.

B5 — CANONICAL BILLING RESOLVER
==================================================

Buat satu resolver backend yang digunakan customer dan admin.

Output minimum:

{
  invoiceStatus,
  paymentStatus,
  billingStatus,
  invoiceId,
  totalAmount,
  paidAmount,
  remainingBalance,
  proofSubmitted,
  verificationStatus,
  paymentDestinationAvailable,
  filesUnlocked
}

invoiceStatus:

- not_created
- issued
- partially_paid
- paid
- void

paymentStatus:

- not_submitted
- submitted
- under_review
- verified
- rejected

billingStatus:

- billing_pending
- awaiting_payment
- payment_under_review
- paid

Rules:

- invoice tidak ada → billing_pending;
- invoice ada + saldo > 0 + proof belum dikirim → awaiting_payment;
- proof dikirim → payment_under_review;
- proof ditolak → awaiting_payment/rejected state;
- verified sebagian → partially_paid;
- verified penuh → paid;
- frontend tidak menentukan billing state hanya dari remainingBalance.
