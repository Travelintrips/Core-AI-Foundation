===========================================================
TUJUAN
======

Saat ini banyak route dan service melakukan query database langsung.

Hal ini menyebabkan tenant filtering, soft-delete filtering, audit logging, dan transaction handling berisiko diterapkan berbeda-beda di setiap file.

Bangun repository/domain access foundation yang:

1. menerima canonical `RequestContext`;
2. menerapkan tenant scope secara default;
3. tidak mempercayai tenantId dari input client;
4. siap mendukung soft delete tanpa mengimplementasikan kolomnya sekarang;
5. siap mengeluarkan canonical audit event pada WP berikutnya;
6. mendukung transaction context;
7. tidak menjadi generic repository berlebihan;
8. dapat diadopsi bertahap tanpa membangun ulang aplikasi.

===========================================================
PRINSIP WAJIB
=============

* Route tidak boleh menjadi tempat utama query tenant-owned data.
* Service tidak boleh membuat tenant scope sendiri secara ad hoc.
* Repository tenant-owned wajib menerima canonical RequestContext.
* Tenant scope harus menjadi default, bukan parameter opsional biasa.
* Bypass tenant harus eksplisit, terbatas, dan dapat diaudit.
* Platform admin tidak otomatis berarti seluruh query bebas tenant.
* Public token flow tetap memakai resource-derived tenant.
* Jangan membuat satu BaseRepository besar yang menangani semua domain.
* Jangan memindahkan seluruh codebase sekaligus.
* Implementasikan fondasi dan migrasikan domain prioritas sesuai spesifikasi.

TAHAP 3 — REPOSITORY CONTEXT CONTRACT
=====================================

Gunakan canonical `RequestContext` yang sudah dibuat pada WP-01.

Buat contract kecil yang diperlukan repository, misalnya secara konseptual:

* request context
* transaction/database executor
* includeDeleted untuk penggunaan masa depan
* audit metadata untuk penggunaan masa depan
* explicit platform operation mode
* resource scope

Jangan membuat context kedua yang bersaing dengan `RequestContext`.

Bila perlu membuat tipe turunan, tipe tersebut harus mengacu langsung ke canonical RequestContext.

Repository tidak boleh menerima kombinasi bebas seperti:

* tenantId dari caller
* actorId terpisah
* isAdmin boolean terpisah

sebagai pengganti canonical context.

===========================================================
TAHAP 4 — TENANT SCOPE GUARD
============================

Bangun helper tenant-scope yang kecil, typed, dan reusable.

Helper harus:

* memastikan tenantId tersedia untuk tenant-owned operation;
* menolak missing tenant context;
* menolak tenant mismatch;
* membedakan global/reference table dan tenant-owned table;
* tidak dapat dibypass dengan boolean dari input user;
* tidak mencatat secret atau token;
* mempertahankan requestId/correlationId pada error/log;
* kompatibel dengan transaction executor.

Jangan membuat query builder abstrak yang menyembunyikan seluruh SQL/Drizzle behavior.

Tenant condition tetap harus terlihat dan dapat ditinjau pada repository domain.

===========================================================
TAHAP 9 — PLATFORM ADMIN BYPASS
===============================

Definisikan jalur eksplisit untuk operasi platform-wide.

Aturan:

* platform admin bypass tidak boleh otomatis aktif hanya karena role;
* caller harus memilih operasi platform scope secara eksplisit;
* helper harus memverifikasi actorType dan permission;
* operasi bypass harus memiliki alasan/operation name;
* siapkan metadata untuk audit log WP-03;
* jangan expose bypass ke request body/query/header;
* tenant-owned mutation lintas tenant harus tetap dilarang kecuali operasi administratif yang spesifik.

Tambahkan negative tests untuk bypass palsu.

===========================================================
TAHAP 10 — ERROR MODEL
======================

Gunakan model error proyek yang sudah ada.

Minimal behavior:

* missing tenant context → safe failure;
* cross-tenant resource → 404 atau 403 sesuai surface;
* repository resource tidak ditemukan → tidak bocorkan tenant lain;
* unsupported platform operation → forbidden;
* invalid public-resource scope → safe not found/forbidden;
* transaction failure → rollback dan error konsisten.

Jangan membuat response error internal berbeda-beda di setiap repository.

===========================================================
TAHAP 11 — TESTS
================

Tambahkan unit dan integration tests.

A. Repository Tenant Enforcement

* Tenant A membaca resource Tenant A → berhasil.
* Tenant A membaca resource Tenant B → gagal aman.
* Tenant A update resource Tenant B → gagal.
* Tenant A delete/uninstall resource Tenant B → gagal.
* List hanya berisi data tenant aktif.
* Count/analytics tidak mencampur tenant.
* ID resource valid tetapi tenant salah tidak membocorkan keberadaan.
* Missing context gagal.

B. Context Integrity

* repository tidak menerima tenant override;
* legacy adapter tidak dapat mengganti canonical tenant;
* platform bypass memerlukan permission eksplisit;
* public-token context hanya bekerja dalam resource scope.

C. Transaction

* executor transaksi digunakan;
* failure melakukan rollback;
* repository tidak memakai global client selama transaksi;
* context tetap sama dalam seluruh transaksi.

D. Marketplace Regression

* seluruh test WP-00 tetap lulus;
* install/list/upgrade/enable/disable/uninstall tenant-safe;
* analytics tenant-scoped;
* spoofing tetap mendapat 403.

E. Public Catalog Regression

* public quote/request-service happy path tetap bekerja;
* tenant client input tetap diabaikan;
* resource tersimpan pada tenant canonical;
* cross-tenant manipulation gagal.

F. Quotation Foundation

* canonical dan legacy read dilakukan melalui method eksplisit;
* tidak ada accidental dual write;
* existing customer-facing flow tidak berubah.

G. Direct Query Guard

Tambahkan test/lint-like verification yang masuk akal untuk mencegah route prioritas kembali melakukan direct mutation tenant-owned.

Jangan membuat regex rapuh untuk seluruh codebase bila menimbulkan banyak false positive.
