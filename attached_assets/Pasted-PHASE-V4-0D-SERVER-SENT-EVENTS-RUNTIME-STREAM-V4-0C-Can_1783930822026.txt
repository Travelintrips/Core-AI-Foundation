PHASE V4.0D — SERVER-SENT EVENTS RUNTIME STREAM

V4.0C Canonical Runtime Event Model telah selesai dan disetujui.

Canonical event source:

canonicalEventService.ts

Source of truth:

creative_project_steps
creative_ai_assets
creative_ai_client_reviews
creative project row

CanonicalEvent model sudah final dan tidak boleh diubah secara breaking.

Jangan membuat event model kedua.

Jangan membuat WebSocket pada fase ini.

Jangan mengaktifkan ai_jobs/dispatcher.

==================================================
LANGKAH 2 — SSE ENDPOINT
==================================================

Tambahkan endpoint customer-safe, misalnya:

GET /api/public/customer/workspace/:token/projects/:projectNumber/events/stream

Gunakan route convention existing.

Endpoint wajib:

- validate workspace token;
- resolve project ownership server-side;
- reject cross-project access;
- set Content-Type: text/event-stream;
- set Cache-Control: no-cache, no-transform;
- set Connection: keep-alive;
- set X-Accel-Buffering: no;
- flush headers jika tersedia;
- send heartbeat;
- clean up resources saat connection close.

Jangan menerima arbitrary internalProjectId dari client.

==================================================
LANGKAH 3 — INITIAL SNAPSHOT
==================================================

Saat connection dibuka:

1. validasi access;
2. kirim event `snapshot`;
3. snapshot berisi canonical events terbaru dan metadata koneksi;
4. frontend dapat menyinkronkan ulang state.

Contoh:

event: snapshot
id: snapshot:{timestamp}
data: {
  events: CanonicalEvent[],
  lastEventId: string | null,
  generatedAt: string
}

Batasi jumlah initial events agar payload tidak terlalu besar.

Gunakan configurable limit.

==================================================
LANGKAH 4 — EVENT CURSOR
==================================================

Jangan membandingkan `createdAt > Last-Event-ID`.

`Last-Event-ID` adalah event identifier.

Implementasikan cursor yang aman.

Pilihan yang disarankan:

A. Gunakan canonical event ordering tuple:

createdAt + eventId

B. Tambahkan helper internal:

CanonicalEventCursor {
  createdAt: string;
  eventId: string;
}

Encode cursor menjadi string customer-safe, misalnya base64url JSON.

Atau gunakan query parameter:

?after=<encoded-cursor>

Jika browser reconnect native hanya mengirim Last-Event-ID, isi SSE `id:` dengan encoded cursor, bukan raw canonical eventId.

Canonical eventId tetap berada di payload.

Contoh:

id: eyJjcmVhdGVkQXQiOiIyMDI2...}
event: runtime.event
data: {
  event: CanonicalEvent
}

Cursor comparison:

- createdAt lebih besar; atau
- createdAt sama dan eventId lexicographically lebih besar.

Ini mencegah event hilang saat beberapa event mempunyai timestamp sama.

==================================================
LANGKAH 5 — POLLING ADAPTER SERVER-SIDE
==================================================

Karena source tables belum memiliki push notification, SSE server boleh melakukan internal polling terhadap canonicalEventService.

Persyaratan:

- interval configurable, misalnya 2–5 detik;
- jangan query per connection bila dapat dihindari;
- cegah N connections menghasilkan N×4 DB queries;
- gunakan shared project stream/poller per project;
- fan-out ke subscribers project yang sama;
- stop poller saat subscriber terakhir disconnect;
- deduplicate events dengan canonical eventId/cursor;
- sort events sebelum publish;
- handle query failure tanpa menutup stream langsung.

Jangan membuat cache kompleks.

Gunakan lightweight in-memory project channel registry bila sesuai.

==================================================
LANGKAH 6 — HEARTBEAT
==================================================

Kirim heartbeat setiap 15–30 detik.

Contoh:

event: heartbeat
data: {
  timestamp: string
}

Heartbeat:

- tidak masuk activity feed;
- tidak disimpan;
- menjaga proxy connection tetap hidup;
- membantu frontend mengetahui stale connection.

==================================================
LANGKAH 7 — EVENT TYPES
==================================================

Gunakan tipe SSE:

- snapshot
- runtime.event
- heartbeat
- stream.warning
- stream.error

`runtime.event` harus membawa CanonicalEvent tanpa mengubah modelnya.

Jangan expose internal exception pada `stream.error`.

Contoh customer-safe:

“Live updates are temporarily unavailable. Reconnecting…”

Jangan memasukkan secret selain workspace token yang memang sudah digunakan route public workspace.

==================================================
LANGKAH 9 — SNAPSHOT + STREAM MERGE
==================================================

Frontend harus:

1. load snapshot REST existing;
2. connect SSE;
3. receive snapshot SSE;
4. merge events by canonical eventId;
5. sort by createdAt + eventId;
6. ignore duplicates;
7. update activity feed/timeline/current task;
8. refetch full project snapshot bila stream kehilangan sinkronisasi.

Jangan append blindly.

Gunakan deterministic merge helper.

==================================================
LANGKAH 10 — RECONNECT
==================================================

Native EventSource reconnect dapat digunakan, tetapi tambahkan UX state.

Handle:

- temporary disconnect;
- server restart;
- browser sleep;
- laptop wake;
- network offline/online;
- token expired;
- project completed;
- tab visibility change.

Saat reconnect:

- browser sends Last-Event-ID cursor;
- server sends missed events;
- client may refetch snapshot after long disconnect;
- deduplicate all events.

Jika reconnect gagal berulang:

- fallback ke periodic snapshot polling;
- tampilkan status “Updates delayed”;
- jangan membuat modal alarm.

LANGKAH 13 — NO-RUNTIME PROJECTS
==================================================

“Live AI activity will appear when production starts.”

==================================================
LANGKAH 14 — COMPLETED PROJECTS
==================================================

Untuk project completed:

- kirim snapshot final;
- stream boleh tetap hidup singkat atau ditutup dengan event final;
- frontend tidak perlu reconnect terus-menerus;
- stop streaming setelah terminal state bila aman.

Jika stream ditutup secara sengaja, kirim:

event: stream.complete

dan frontend menandai project final, tanpa reconnect loop.
